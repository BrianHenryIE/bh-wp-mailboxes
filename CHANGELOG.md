# Changelog

## Unreleased

* Fix: an IMAP connection failure now says which server, port and encryption were used, PHP's reason for the failure (recovered from the warning ImapEngine silences with `@`), and the socket error code, and, when PHP gives no reason at all, that the environment cannot open outbound connections (e.g. WordPress Playground in the browser, which has no TCP sockets). Previously the whole message could be `Unable to connect to tls://host:993 ()`. `ImapEngine_Imap_Email_Connection` still throws ImapEngine's `ImapConnectionFailedException` (with the original as the previous exception), so callers are unaffected
* Breaking: IMAP connections now validate the server's TLS certificate by default (`validate_cert` was hardcoded to false). `IMAP_Credentials_Interface` gains `should_validate_cert(): bool`; `Imap_Credentials` takes it as a fifth constructor argument (default true) and stores it as `validate_cert` in its JSON (a record saved without the key validates); `Imap_Credentials_Env` reads `IMAP_VALIDATE_CERT` (only `false`, `0`, `no` or `off` turn validation off). An existing account on a self-signed certificate must be edited once to untick "Validate the server's certificate"
* Add: a "Validate the server's certificate" checkbox in the add/edit IMAP account modal (posted as `validate_cert`; `Email_Accounts_Ajax::save()` / `test_connection()` take a `bool $validate_cert = true`) and in the development plugin's IMAP form
* Add: `bh_wp_mailboxes_imap_mailbox_config` filter over the ImapEngine mailbox configuration (`host`, `port`, `username`, `password`, `encryption`, `validate_cert`) before the connection is created, with the consumer's plugin slug, the credentials and the account, so e.g. `debug`, `timeout` or `proxy` can be set. `ImapEngine_Imap_Email_Connection`'s constructor takes the plugin slug as an optional third argument
* Add: a "Test connection" button in the add/edit IMAP account modal tries the entered details against the server before anything is saved, reporting the result (or the server's error) in the form. Served by `Email_Accounts_Ajax::handle_test_connection()` (`wp_ajax_bh_wp_mailboxes_test_account_connection_{accounts_cpt}`) / `Email_Accounts_Ajax::test_connection()`, which share the save handler's validation (a blank password when editing tests with the saved one)
* Fix: "Check now" and "Check all" always reported success, even when an account's server rejected the login, was unreachable, had no saved credentials or no usable connection: every failure in `API::fetch_for_account()` degraded to "no new emails". `Check_Email_Account_Result` now carries the outcome (`success`, `skipped` for disabled / receive-only / cron-rate-limited accounts, a user-facing `message` for a skip or failure, and `warnings` for a completed fetch whose post-download action or refreshed-credentials save failed); `Check_Mailbox_Result::success` is false when any account failed (skips are not failures), with `get_failures()` / `get_skipped()`. The per-account "Check now" AJAX handler responds with an error (`message`, `status`: `failed`|`skipped`) and the re-rendered accounts table, so the row's last-failure time and login-failure badge update in place; the notice is red for a failure and yellow for a skip. The mailbox-wide "Check all" handler, whose JS read a `new_emails` key that was never sent (so it never counted new emails or highlighted their rows), now sends the new-email count and ids plus a per-account `{name, email_address, status, message, new_email_count, warnings}` list; its notice names each failed account with its message
* Breaking: the library now stores account credentials itself, encrypted, using the WordPress Secrets API (the `wordpress/secrets-api` feature plugin, a new Composer dependency). on the first credential read or write (never at bootstrap, so requests that do not touch credentials do no Secrets API work) the store locates the package through Composer's runtime API (`composer-runtime-api` is now a requirement), includes its `secrets.php` and registers an autoloader for its classes (never its plugin bootstrap) and the store builds its own `WP_Secrets_Libsodium_Provider` over `WP_Secrets_Option_Store` (keyed by `WP_Secrets_Config_Key_Provider`) rather than calling `wp_get_secret()` etc., so a site's `secrets.php` drop-in (`$GLOBALS['wp_secrets_store']` and friends) does not redirect where this library's credentials go; consumers prefix the copy's names at build time so it is independent of core's or an activated plugin's implementation. The `bh_wp_mailboxes_credentials` filter is removed: `API::fetch_for_account()`, `test_connection()`, the remote email actions, the accounts table and the Gmail CLI read the account's saved credentials instead. `API_Interface` gains `get_account_credentials( $account )`, `save_account_credentials( $account, $credentials )` (IMAP or Gmail credentials; env- and file-backed implementations are captured by value) and `delete_account_credentials( $account )`; `delete_email_account()` also discards the credentials. New `API\Credentials_Store_Interface` / `API\Secrets_Credentials_Store` (one secret per account, `{plugin-slug}/{accounts-post-type}-{address}`, e.g. `my-plugin/my_plugin_accounts-inbox-at-example-com`), `API\Refreshes_Credentials`, and `Connections\Gmail_API\Gmail_Credentials` value object (which replaces the file-backed `Google_API_Credentials`: `Gmail_Credentials::from_files()` reads Google's client secret and token files once). `Account_Credentials_Interface` now extends `JsonSerializable`: implementations serialise their values plus a `type` key (`IMAP_Credentials_Json_Trait` / `Google_API_Credentials_Json_Trait` do so through the getters) and `Imap_Credentials::from_array()` / `Gmail_Credentials::from_array()` rebuild them; `Imap_Credentials` and `Gmail_Credentials` expose public readonly properties. Consumers that provided credentials via the filter must save them once with `save_account_credentials()`
* Breaking: the Gmail connection no longer writes a refreshed access token to `token.json` inside the library, nor prompts on STDIN for authorisation; a refreshed token is saved to the account's credentials after a fetch or connection test (`Refreshes_Credentials`), and an expired token with no refresh token is an error. `wp {cli-base} gmail refresh-access-token` saves the new token to the credentials store instead of printing it and firing `bh_wp_mailboxes_gmail_access_token_refreshed` (removed)
* Add: the emails list's per-account status cards are replaced by an accounts table (`Admin\Status_View`) with "Add account", per-row enable/disable, edit and delete actions, and a "Check now" button that keeps the set-fetch-since date utility; receive-only accounts (e.g. REST ingress) show "N/A" and cannot be checked or deleted. Adding/editing opens a modal with the IMAP fields; the library saves the account and its credentials (an empty password when editing keeps the saved one). Served by `Admin\Email_Accounts_Ajax`, which also takes over the per-account "Check now" handler from `Emails_List_Table_Ajax` (now only the mailbox-wide "Check all"); the unused `wp_ajax_bh_wp_mailboxes_set_fetch_since_{accounts_cpt}` alias is removed
* Add: the accounts table is a `WP_List_Table` (`Admin\Email_Accounts_List_Table`, keyed to the accounts CPT screen) with no checkbox column, bulk actions or table nav; enable/disable, edit and delete are row actions on the account column, and "Check now" / "Check since…" are row actions under the last fetched time
* Add: `Admin\Email_Account_Modal` — the add/edit IMAP account modal (with its delete confirmation and nonce) extracted from the accounts table so consumers can print it, with `print_add_button()`, on their own screens (e.g. a WooCommerce payment gateway settings page). It has its own script and stylesheet (`js/account-modal.js`, `css/account-modal.css`, handle `Email_Account_Modal::get_script_handle()`), so nothing unrelated is enqueued; the accounts table / emails list script (`js/bh-wp-mailboxes.js`, `css/accounts-table.css`) depends on it
* Add: `Connections\Imap\Imap_Credentials` value object; `API_Interface` gains `configure_email_account()`, `set_email_account_active()` and `delete_email_account()`
* Fix: the accounts modal's save handler refused to be keyed only by email address: saving the address of a non-IMAP account (e.g. the REST ingress) now responds 400 instead of converting it into an IMAP account; "Check now" responds 400 for receive-only accounts; enable/disable responds 404 when the account has gone; unexpected save/status errors are logged and reported generically rather than echoing the exception message; validation messages are no longer HTML-escaped (they are rendered as text)
* Add: the development plugin's settings page demonstrates the reusable `Email_Account_Modal` on a consumer's own screen (adds accounts to Mailbox One); its IMAP, `.env.secret` and Gmail forms and `wp development-plugin gmail connect` save credentials with `API::save_account_credentials()` (the transient/wp_option credential stores are removed)
* Fix: no mailboxes were registered in the self-contained WordPress Playground build — `BH_WP_Mailboxes::filter()` derived the plugin slug from the library file's path, which never matched when the library is nested in a plugin's vendor directory; instances are now matched by their own settings' plugin slug
* Add: `composer playground-serve` — build the development plugin and serve it in WordPress Playground locally (the same self-contained layout the CI preview workflow publishes)
* Breaking: `API::add_email_account()` (which threw when an account already existed) is replaced by `API::configure_email_account()` — an upsert keyed by the account's email address, its only required parameter: creates the account when none exists (throwing `InvalidArgumentException` if the then-required display name or connection class is missing), otherwise updates it in place (null values leave existing configuration unchanged, including the connection class)
* Fix: the REST ingress endpoint accepted emails for a disabled (inactive) account; it now responds 403 `rest_account_disabled`
* Fix: `Email_Account_WP_Post_Repository::get_all()` / `API::get_email_accounts()` returned at most ten accounts (WP_Query's default page size)
* Add: `API::set_email_account_active( $email_address, $active )` — enable/disable an account without deleting it (inactive accounts are skipped by cron); returns the updated account, or null when no account exists for the address
* Add: `API::delete_email_account( $email_address )` — permanently deletes the account's post (locally saved emails are kept); returns false when no account exists for the address
* Breaking: library hooks now pass `$plugin_slug` first (after the filtered value), followed by the emails post type on per-mailbox hooks: `bh_wp_mailboxes_credentials`, `bh_wp_mailboxes_connection_for_account`, `bh_wp_mailboxes_auth_failure_notice_message` (filters) and `bh_wp_mailboxes_new_email` (action) gain both; `bh_wp_mailboxes_max_message_size_bytes` (filter) and `bh_wp_mailboxes_gmail_access_token_refreshed` (action) gain only `$plugin_slug`
